# Peer wipe protocol — specification draft (package D)

Status: **implemented behind an off-by-default "Peer wipe (unreviewed)" setting (owner decision
2026-10-28). It is still a draft for independent review.** Both phones must turn the setting on.
The community review at the end of the pipeline covers this document, the code and the vectors.
The plan's gate is a second, independent implementer reproducing `test-vectors/control-v1.properties`.
That gate still applies before the setting can lose its "unreviewed" label.
Requirements: [plan](SECURITY_DEVELOPMENT_PLAN.md) "Emergency operations" and invariants S05,
S06, S07, S10, S11, S12. Local destruction already exists ([local wipe](LOCAL_WIPE_CONTROL.md),
[epochs](ACTIVE_EPOCH_DESIGN.md)). This adds the optional, best-effort request that the *other*
phone in a pairing destroy its copy.

## Implementation notes (where the build differs from the draft below)

| Draft | As built | Why |
| --- | --- | --- |
| Control keys in a separate `<root>-ctl` store | `control` object in the contact vault | One atomic commit with the pairing. Covered by existing retirement, rotation and epoch scope, with no new namespace. |

| Dispatch record holds `C` | Holds the mailbox room and the derived **control capability** (SHA-256 of `C` with its own label), not `C`. The setup token is used only on relays without claims. | Less retained authority. |
| ACK record kept until accepted | The recipient keeps only the true final ACK and re-posts it for 7 days. | Covers a slow initiator. |
| Status for old pairings | Wipe result says the friend "could not be asked: this chat was paired before peer wipe existed" | §8 wording |

## Goals and non-goals

- A wipe on phone A asks phone B to destroy **only the A↔B relationship** on B.
- Local destruction on A never waits for the request to be sent, accepted or acknowledged.
- After A's wipe, A keeps **no reusable authority**: only sealed, single-purpose blobs.
- Works after pad exhaustion and after ordinary relay access is revoked (S11).
- B acts only on a command authenticated with keys B received in person from A.
- Status shown to the user is evidence-based: a relay acceptance is not a peer action, and a
  peer report is not proof of forensic erasure.

Non-goals: forcing a modified or permanently offline phone to comply; remote wiping of any
data other than the pairing; wiping chats with third parties; any remote unlock or enrollment.

## 1. Control material (provisioned in person)

During physical pairing (USB or NFC-assisted Wi-Fi, after both people compare codes), each
phone generates and sends, inside the already-authenticated encrypted pairing channel:

| Item | Size | Generated by | Purpose |
| --- | ---: | --- | --- |
| Pairing generation `G` | 16 B | role A | Names this pairing; never reused |
| `K_ctl[A→B]` | 32 B | A | Authenticates A's commands to B |
| `K_ctl[B→A]` | 32 B | B | Authenticates B's commands to A |
| `K_ack[A→B]`, `K_ack[B→A]` | 32 B each | sender | Authenticates acknowledgements |
| Control relay credential `C` | 32 B | role A | Scoped access to the control mailbox only |

Each phone stores its outgoing and incoming keys in a separate encrypted store
(`<root>-ctl`), not in the operational vault and not derived from pad bytes. Control keys
never touch the relay. Existing pairings have no control material; see §8.

## 2. Wire format `OTPCTL01`

Canonical fixed-length frames. Reject unknown magic or kind and any length mismatch before
touching state.

```
WIPE (89 bytes)
  magic        8  "OTPCTL01"
  kind         1  0x01 = WIPE
  direction    1  0x01 = A→B, 0x02 = B→A
  generation  16  G
  request     16  random per wipe request
  issued       8  sender clock, ms since epoch (informational, never trusted)
  tag         32  HMAC-SHA256(K_ctl[dir], all preceding bytes)
  (+ 7 bytes reserved zero, included in the tag)

ACK (60 bytes)
  magic        8  "OTPCTL01"
  kind         1  0x02 = ACK
  direction    1  direction of the acknowledging phone
  generation  16  G
  outcome      1  0x01 RECEIVED, 0x02 WIPED, 0x03 INCOMPLETE
  reserved     1  zero
  tag         32  HMAC-SHA256(K_ack[dir], all preceding bytes)
```

The ACK deliberately does **not** bind the request id. Every ACK for a generation can then be
precomputed before keys are destroyed (§4, §5), and a replayed ACK is harmless because the
generation is terminal on both sides. Domain separation comes from distinct keys plus `kind`.

## 3. Relay control mailbox

- Address `R_ctl = HKDF-SHA256(C, info="OTP Pager control room v1")`, distinct from the
  message mailbox; authorized only by `C` (registered at pairing like today's per-chat
  capability, F06 work in package E).
- Durable priority queue: control frames are fetched before ordinary traffic and survive
  message-mailbox revocation, relay restart and container redeploy.
- Bounded: at most 8 frames per mailbox, 128 bytes each; duplicates collapse. Retention is
  `T_ctl` (proposed 90 days); expiry is reported to the user as "request expired, outcome
  unknown", never as success.
- The relay can delay, drop or replay frames, and can see that a control frame exists. It
  cannot forge or alter one.

## 4. Initiator (phone A) — wipe this chat / wipe all

Under the lifecycle lock, **before** any local destruction step:

1. Build `WIPE` with a fresh request id and its tag using `K_ctl[A→B]`.
2. Precompute the three ACK frames B could send (`RECEIVED`, `WIPED`, `INCOMPLETE`) using
   `K_ack[B→A]`; keep only their SHA-256 hashes.
3. Write a minimal **dispatch record** (its own small authenticated file, outside the
   operational vault): `G`, `R_ctl`, `C`, the sealed WIPE frame, the three expected ACK hashes,
   creation time and state (`QUEUED`). No pad, message, control key or identity key.
4. Destroy the pairing locally exactly as today (marker, keys, files). This includes
   `<root>-ctl`, so A can never mint another command for `G`.

If any of steps 1–3 fails, local destruction proceeds anyway and the UI says the friend could
not be asked (S05). A separate background sender posts the sealed frame until the relay
accepts it (`ACCEPTED`), then polls for ACKs and matches them by hash:

| Evidence | User-facing status |
| --- | --- |
| Dispatch record could not be written | "Your friend's phone could not be asked to wipe" |
| Queued, not yet accepted | "Request waiting to be sent" |
| Relay accepted | "Request delivered to the server (not yet seen by your friend's phone)" |
| ACK RECEIVED matched | "Your friend's phone received the request" |
| ACK WIPED matched | "Your friend's phone reported the wipe complete" |
| ACK INCOMPLETE matched | "Your friend's phone reported the wipe did not finish" |
| `T_ctl` passed | "Request expired; outcome unknown" |

The dispatch record keeps routing metadata and `C` by design: this is the documented
retained-metadata exception. **Forget request** deletes it and gives up on status.

Wipe all: one dispatch record per pairing that has control material; failure of one never
blocks the others (S12).

## 5. Recipient (phone B)

On fetching a frame from `R_ctl`:

1. Parse strictly; find the pairing whose `G` matches; reject if none or if `direction` is not
   the peer's. Verify the tag with the stored `K_ctl[peer→self]` in constant time.
2. If the pairing is already terminal: re-send the stored ACK (idempotent) and stop.
3. Otherwise, under the lock: precompute `RECEIVED`, `WIPED` and `INCOMPLETE` with
   `K_ack[self→peer]`, write them into a minimal ack record, post `RECEIVED`, and retire the
   pairing with the existing local primitive. The primitive deletes `<root>-ctl` too, so no
   key survives for later ACKs.
4. When local cleanup is verified, post `WIPED`; otherwise `INCOMPLETE`. Delete the unused
   precomputed ACK. Keep the sent one until the relay accepts it, then delete the record.

B touches only the matching pairing; every other contact stays usable. B shows a neutral
notice naming the chat ("Alex's phone asked to remove this chat; it was removed on this
phone"). There is no confirmation step: the person who paired in person already holds this
authority.

## 6. Ordering, duplicates and simultaneous wipes

- Duplicate or replayed WIPE: the pairing is already terminal → idempotent ACK only.
- Reordered frames: ACK hashes are matched as a set; arrival order does not matter.
- Both phones wipe at once: each destroyed its own copy first. Each later receives the
  other's WIPE, finds the pairing terminal and re-sends its stored ACK if one exists. A has
  no ack record for B's request (A wiped first), so B's status may stay "delivered". That is
  acceptable and shown honestly; both copies are gone.
- A WIPE for an unknown `G` (already fresh-paired, or a different pairing): ignored, and never
  applied to the new pairing, because a fresh pairing gets a new `G` and new keys (S07).

## 7. Interaction with epochs and global wipe

Dispatch and ack records are retained-metadata files, listed in a terminal record's scope.
They are not destroyed by the epoch wipe that created them, so delivery can continue
afterwards. They are destroyed by an explicit "Forget all requests" or when complete.
A fresh enrollment never revives a control key; old `G` values are added to the retained
cohort so they can never be accepted again.

## 8. Migration of existing pairings

Existing pairings have no control material, and retrofitting it remotely would hand authority
to whoever controls the relay. Options, in order of preference:

1. Fresh physical pairing (already supported).
2. A small in-person **control upgrade** over the existing authenticated USB / NFC+Wi-Fi
   channel: same code comparison, transfers only §1 items for the existing pairing.

Until then the UI says: "This chat can only be wiped on this phone. Pair again in person to
let a wipe reach your friend's phone."

## 9. Security analysis summary (for reviewers)

| Threat | Result |
| --- | --- |
| Relay forges or alters a WIPE | Impossible without `K_ctl`; HMAC-SHA256 |
| Relay replays an old WIPE | Applies only to the same `G`, which is terminal after one use |
| Relay drops or delays | Request stays unconfirmed; status says so; local wipe already done |
| Stolen initiator after wipe | Holds only sealed frames and ACK hashes; cannot mint commands |
| Stolen recipient before the request arrives | Out of scope for this protocol (see appendix A) |
| Modified peer ignores the request | Cannot be prevented; "reported" wording only |
| Cross-pairing confusion | `G` + direction + per-pairing keys; unknown `G` ignored |
| Pad exhaustion | Control keys are independent of pads (S11) |

Open questions for review: `T_ctl` value; whether ACK should be signed with the device key
in addition to HMAC (adds attribution, loses deniability); exact relay bounds; whether B should
also wipe a draft or notification history held by the OS; vector set coverage.

## 10. Vectors and implementation gate

Before any destructive code: a reference implementation (Python, outside the app) produces
vectors for WIPE and ACK frames, the HKDF mailbox address and the precomputed ACK hashes, and
a **second implementer** reproduces them independently. Kotlin tests then consume the vectors.
Vectors produced by the same author as the spec are not independent; this requirement
cannot be met inside a single development session.

## Appendix A — optional "strict" chats (owner idea, 2026-10-27)

A per-chat, opt-in mode for high-risk use, chosen at pairing time on both phones. The chat's
vault key is wrapped by a combination of the phone's Keystore key and a 32-byte share held by
the relay under the control credential. Opening the chat fetches the share (the share alone
decrypts nothing). A WIPE also deletes the share on the relay, and a check-in deadline (for
example 12 hours) makes the relay discard it. A seized phone kept offline then cannot open
strict chats even with a full storage copy.

Costs: no access when the relay is unreachable; the relay operator can lock users out and sees
when chats are opened; a permanently lost share loses those chats. This is a design note for
review together with this protocol, not a commitment.

## Recipient local-first correction (review candidate, 2026-10-28)

`fix/peer-wipe-local-first` corrects the implemented recipient ordering: precompute
final ACKs without networking, retire locally even if ACK preparation/persistence
fails, persist the observed final outcome, then pump transport. No preliminary
RECEIVED POST is required. This supersedes the draft §5 step that posts RECEIVED
before retirement. A blocked network cannot postpone retirement, although the sync
worker may still wait on dispatch after destruction. Missing/failed ACK storage
means the peer may never learn the result; no success is fabricated. Local status
now distinguishes completed from incomplete retirement. Separate restart recovery
of unfinished ACK records remains outstanding; this change does not solve it.
